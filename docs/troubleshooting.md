# 故障排查

先看两个地方：控制台顶部的**提醒条**（会直接指出规则源失败、上游全部不可用、需要重启等问题），以及 **日志** 页面（每条请求的处理结果和耗时）。下面按现象分类。

## 服务起不来

**`bind: address already in use`（端口被占用）**
- 53 端口常被 `systemd-resolved`（`127.0.0.53:53`）占用。监听具体的局域网地址而不是 `:53`，或按 [部署与运维](deployment.md#监听-53-端口) 关闭它的 stub 监听。
- 用 `ss -lunp | grep :53` 找出占用者。同一台机器上重复启动了 DNSentry 也会出现这个错误。

**`permission denied` 监听 53 端口**
- 1024 以下端口需要权限。systemd 单元里已配置 `CAP_NET_BIND_SERVICE`；手动运行时用 `sudo setcap cap_net_bind_service=+ep ./dnsentry`，或者改用 Docker。

**启动时报配置错误**
- 用 `dnsentry -check -config <路径>` 只做校验不启动，错误信息会指出具体字段（例如 `invalid upstreams[1]`）。
- 配置文件被手工改坏时，可以从 `data/history/` 里挑一份旧版本覆盖回去；或在控制台「配置历史」页恢复（服务能启动时）。

**控制台打不开**
- 默认只监听 `127.0.0.1:18080`，从别的机器访问会连接被拒绝。要公开访问必须同时设置监听地址和令牌，见 [部署与运维](deployment.md#访问控制台)。
- 在 Docker 里，控制台监听地址必须是 `0.0.0.0:18080`（Compose 文件已设置），并且要映射端口和设置 `DNSENTRY_API_TOKEN`。
- 页面提示需要令牌：在控制台登录框输入 `DNSENTRY_API_TOKEN` 的值。连续输错 10 次会被限制 1 分钟。

## 设备上网慢或解析失败

1. 在控制台「配置 → 上游」点**测试**，看每个上游是否可达、延迟多少。
2. 看仪表盘的「上游延迟」和「最慢 / 失败域名」，判断是所有上游都有问题，还是个别域名的问题。
3. 用命令行直接问 DNSentry，排除设备自身的问题：

   ```sh
   dnsentry-query -server <DNSentry 地址>:53 example.com
   ```

常见原因：

| 现象 | 可能原因与处理 |
| --- | --- |
| 所有上游都超时 | 服务器自己上不了网，或防火墙拦了 853 / 443 出站；加一个普通 DNS 作为备用上游（`fallback_upstreams`）。 |
| DoH / DoT 上游偶尔失败 | 上游域名需要先解析，检查 `bootstrap_dns` 是否可达。 |
| 只有某个域名解析失败 | 看是否命中了「域名分流」，分流的上游不会回退到默认上游；用 **规则检测** 和「日志」确认走了哪条路径。 |
| 公司 / 内网域名解析不了 | 为这些域名添加分流，指向内网 DNS。 |
| 返回 `SERVFAIL` 且开启了 DNSSEC 验证 | 该域名的 DNSSEC 签名有问题，或上游不返回 DNSSEC 记录；临时关闭验证确认。 |
| 上游状态一直「冷却中」 | 连续失败的上游会被暂时跳过（30 秒起，最长 5 分钟）；修好网络后会自动恢复，也可以点测试立刻探测。 |

## 某个网站打不开 / 广告没拦住

**网站打不开，怀疑被误拦**
1. 到 **规则** 页用「规则检测」输入域名，会显示命中的规则、来自哪个来源，以及是拦截还是放行。
2. 想放行：添加一条放行规则，例如 `@@||example.com^`。放行总是优先于拦截。
3. 如果检测显示没有被拦截，问题不在过滤上，按上一节排查解析。

**广告没有被拦截**
- 设备可能没有走 DNSentry：在设备上访问一个必被拦截的域名（比如自己加一条 `||blocked.test^` 再解析它），看「日志」有没有出现这条请求。没有就说明设备用了别的 DNS，见下节。
- 浏览器的「安全 DNS / 加密 DNS」（DoH）会绕过系统 DNS，需要在浏览器里关闭，或在路由器上阻止，见 [强制所有设备使用 DNSentry](enforce-dns.md)。
- 应用内置广告（与内容同域名）无法靠 DNS 过滤，这是 DNS 过滤的固有局限。
- 规则源刚添加还没下载成功：到 **规则源** 页看状态和错误信息。

## 设备没有使用 DNSentry

- 「日志」里看不到该设备的请求，或客户端一栏是路由器地址。
- 检查设备的 DNS 设置：**不要配置备用 DNS**，否则系统会随机使用它。
- IPv6 常被忽略：路由器可能通过 RA 下发了运营商的 IPv6 DNS。在路由器上关闭 IPv6 DNS 下发，或同样指向 DNSentry。
- 设备开启了私人 / 加密 DNS（Android 的「私人 DNS」、iOS 的 DNS 配置文件、浏览器 DoH）会绕过 DHCP 下发的地址。
- 客户端显示为路由器地址：说明路由器做了 DNS 转发再交给 DNSentry，看不到真实设备。让 DHCP 直接把 DNSentry 的地址发给设备。

## 规则源问题

在 **规则源** 页每个源都有状态、上次成功时间和错误信息。

| 错误 | 处理 |
| --- | --- |
| 下载超时 / 连接失败 | 服务器访问不了该地址（很多规则托管在 GitHub 上，可能需要代理或换镜像）。失败后会退避 10 分钟再重试；已缓存的旧列表继续生效。 |
| `too large` | 单个列表超过 32 MB 上限，换更小的列表。 |
| 规则数为 0 | 列表格式不对（例如网页而不是纯文本），检查地址是否指向原始文件（raw）。 |
| 重启后规则源是空的 | 检查 `data/remote/`（规则文件所在目录下的 `remote/`） 是否可写、磁盘是否已满；缓存文件损坏会被忽略并重新下载。 |

手动刷新：规则源页点「立即更新」，或调用 `POST /api/rules/sources/refresh`。

## 配置保存后没有效果

- 页面顶部出现 **「需要重启」** 提醒：监听地址、控制台地址、规则文件路径、查询日志存储和加密 DNS 这几项要重启后才生效。
- 保存失败并提示校验错误：按提示修正，配置不会被部分写入。
- 用 Docker 时改了监听端口，也要同步修改端口映射。
- 环境变量（例如 `DNSENTRY_DNS_LISTEN`）会覆盖配置文件里的对应值，改了文件却不生效时先检查环境变量。

## 日志页为空 / 磁盘占用增长

- 查询日志被关闭时页面为空；在「服务设置」中开启。
- 日志默认保留 7 天并按天滚动，可以调小保留天数或关闭持久化。文件为 `data/querylog-YYYY-MM-DD.jsonl`，见 [配置参考](configuration.md)。
- 内存里只保留最近 `query_log_size` 条，页面翻页看不到更早的记录时，需要看落盘的日志。

## 加密 DNS 服务（DoT / DoH / DoQ）连不上

- 确认已在「服务设置」中启用加密 DNS，并且已**重启**。
- 证书：需要配置证书和私钥（文件路径或直接粘贴 PEM）。手机上的「私人 DNS」等客户端要求证书有效、受信任且域名匹配。
- 端口：DoT 853/tcp、DoH 443/tcp、DoH3 与 DoQ 走 UDP，防火墙和 Docker 端口映射都要放行对应协议。
- 访问控制（白名单 / 黑名单 / 限速）同样作用于加密 DNS 入口。

## 还是找不到原因

1. 把日志级别调到 `debug`：`dnsentry -log-level debug`（或 `DNSENTRY_LOG_LEVEL=debug`），复现问题后查看输出。
2. 查看 `/api/status` 里的 `upstream_health`、`rule_sources` 和 `security` 计数。
3. 在 GitHub 提交 issue，附上版本（`dnsentry -version`）、相关日志和脱敏后的配置。安全问题请按 [SECURITY.md](../SECURITY.md) 私下报告。
